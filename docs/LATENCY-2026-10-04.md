# Speech-to-status latency: October 4, 2026

We measured the complete path from simulated release through transcription, routing and
real app actions, and separately analyzed existing microphone-command logs. These results
support fast routing and some sub-second dispatches under prepared synthetic conditions.
They do not support a general sub-second voice-to-action claim or a comparative “fastest” claim.

## Controlled synthetic-audio run

We used an Apple M4 Pro with 24 GB RAM, macOS 26.5.1, Swift 6.3.2, and a release build.
The prepared speech model was `openai_whisper-large-v3-v20240930_turbo`, English, with
WhisperKit's default compute configuration. Clips came from `say -v Samantha -r 175`.
We replayed each clip in real time, then released 0.4 seconds after the file ended.
Audio trailing silence therefore also contributes to the time available for transcription
before release. These are file-replay measurements, not microphone or acoustic-loopback tests.

We tested `open Calculator`, `open Downloads`, and `open Notes`, five times each in that
order, reusing one Jev client. The router received fixed public app candidates and no sites.
The executor used the normal native app/folder paths. Unexpected plans were blocked before
execution. Preparation and downloads were excluded; no source compilation ran during samples.
Varta remained open and idle. Desktop focus was not isolated from other applications or user
input. App running/window state was not reset between repetitions, so these are not cold-start
app-launch measurements. Network conditions were uncontrolled. The Jev model identifier was not captured in
these samples; do not attribute these results to a specific provider model version.

The confirmation run produced the following results. Latencies include every completed
attempt, including failures. Percentiles use nearest rank; with five samples, p95 is the maximum.

| Operation | Attempts | Successful final statuses | Median release → status | p95 | Completion boundary |
|---|---:|---:|---:|---:|---|
| Open Downloads | 5 | 5 | 722 ms | 809 ms | Folder-open dispatch accepted; window not independently verified |
| Open Calculator | 5 | 3 | 1,891 ms | 2,341 ms | Final app-focus verification status |
| Open Notes | 5 | 2 | 1,742 ms | 1,758 ms | Final app-focus verification status |
| All operations | 15 | 10 | 1,742 ms | 2,341 ms | Mixed boundaries above |

All 15 transcripts matched the expected command, ignoring case. All 15 selected the expected
intent, arguments and route. All 15 executions reported success. Five app-focus checks reported
`mismatch`, producing failed final statuses. This does not establish that the apps failed to
launch: it establishes that the foreground-window check did not confirm the requested app.
We need an isolated desktop trial and independent observation to distinguish focus changes,
activation issues, and false negatives in verification.

Across all 15 attempts, post-release transcription took 250 ms median / 423 ms p95;
transcript-to-plan took 438 ms / 725 ms; plan-to-final-status took 1,093 ms / 1,193 ms.
These are separate marginal distributions, not additive medians. The app verifier has a fixed
one-second settling delay. Downloads bypasses that verifier, so its total is not directly
comparable to verified app opening as a measure of visible completion.

We retained the initial trial too: 15/15 correct transcripts and routes, 9 successful final
statuses and 6 failed statuses. Its total median was 1,761 ms, p95 2,160 ms. Downloads reported
749 ms median / 888 ms p95. The confirmation added execution/verification diagnostics; we did
not change execution or verification behavior between trials.

## Observational microphone data

We found 44 transcript attempts in the existing app log: 37 had a terminal status and seven
were incomplete or interrupted. Of the 37 terminal statuses, 21 reported success, 13 failure,
and three requested clarification. This spans multiple development builds, including earlier
bugs and intentionally unsupported commands. It is not an accuracy evaluation or a controlled
comparison with the synthetic workload.

Legacy logs start the transcription duration inside the stop task, then record wall-clock
pipeline timestamps. We estimate stop-task-entry → status by adding that same attempt's
transcription duration to its transcript-to-status interval. This excludes any time before
the stop task entered and does not establish the time of physical key release or visible action.
Durations are rounded in the log, and exact source revisions are unavailable per sample.

| Measurement | Samples | Median | p95 |
|---|---:|---:|---:|
| Estimated stop → status, all terminal outcomes | 37 | 2,166 ms | 5,696 ms |
| Estimated stop → status, successful statuses | 21 | 2,283 ms | 5,696 ms |
| Post-stop transcription, all terminal outcomes | 37 | 1,321 ms | 2,992 ms |
| Transcript → plan, all terminal outcomes | 37 | 545 ms | 1,074 ms |

None of the 21 successful final statuses arrived within one second. That is an observation
about this historical sample, not proof that every visible action takes more than one second.

The successful-status breakdown below preserves the coverage gaps. We omit p95 where fewer
than five successful samples exist; such small samples cannot characterize tail behavior.

| Feature | Successful samples | Median estimated stop → status |
|---|---:|---:|
| Browser controls | 3 | 1,729 ms |
| System volume | 4 | 1,810 ms |
| Music playback controls | 3 | 1,928 ms |
| Calendar | 2 | 2,166 ms |
| Append to Notes | 1 | 3,272 ms |
| Music search/play | 3 | 3,867 ms |

No transcripts, note titles, file paths, calendar entries or provider response bodies are
included. A status of success is the app's report, not independent confirmation of correctness.

## What we should improve next

1. Diagnose foreground verification with an isolated desktop. Keep failed checks visible;
   do not remove verification merely to improve a benchmark number.
2. Measure real microphone commands with the new monotonic timing records. We need repeated
   trials for every feature, particularly note/reminder/event creation, before publishing
   per-feature p95 or broad end-to-end claims. The controlled workload above covers only three
   operations and does not create or modify personal notes, reminders, or events.
3. Investigate post-release speech work. Historical microphone commands have substantially
   more remaining transcription time than these short synthetic clips. Compare release delay,
   speech length, pause reuse and model settings on the same audio before choosing a change.
4. Replace the fixed app-verification delay with early checks only after correctness is validated.

For launch copy, we can describe Varta as an open-source macOS voice-command app with
sub-second routing in measured workloads. We should not call it the fastest or promise
universal sub-second voice-to-action performance from this evidence.

## Reproduce

From the repository root:

```bash
swift build --package-path app -c release
mkdir -p eval/results/action-audio
say -v Samantha -r 175 -o eval/results/action-audio/calculator.aiff 'open Calculator'
say -v Samantha -r 175 -o eval/results/action-audio/downloads.aiff 'open Downloads'
say -v Samantha -r 175 -o eval/results/action-audio/notes.aiff 'open Notes'
app/.build/release/varta-cli benchmark-actions eval/results/action-audio 5 > eval/results/actions.json
python3 eval/analyze-timings.py --log "$HOME/.varta/app.log" --output eval/results/voice-timings.json
```

The benchmark makes live Jev requests and opens the three named apps/folders. Its exit status
is nonzero if transcription, routing, or a final status fails; the report still contains those
attempts. Model preparation happens before timing. Clip filenames and expected commands are
fixed; only the directory and repetition count are configurable. Keep other activity off the
desktop for isolated trials. The CLI does not measure acoustic capture or window rendering.

The updated app records `timing` JSON lines using a monotonic clock, from stop-listening entry
to pipeline completion before UI presentation. Fields include post-release transcription,
transcript-to-plan, plan-to-status, total duration, intent, speech reuse source and outcome.
Cancelled/replaced requests are finalized once; follow-ups without routing have no invented
plan stage. The additional records contain no command text or result payload. Existing text
logs retain their previous behavior. Run the analyzer tests with:

```bash
python3 -m unittest discover -s eval -p 'test_timing_analysis.py'
```
